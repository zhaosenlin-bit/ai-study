# ai-study 课堂展示讲义

版本：v0.3  
日期：2026-08-18  
用途：老师课堂投屏讲解，学生课后回看理解。  
项目名：`ai-study`  
仓库：https://github.com/zhaosenlin-bit/ai-study.git

## 1. 今天这节课先建立一个共同画面

我们要做的不是一个普通网页，也不是一个简单聊天框。`ai-study` 是一个小学语文、数学、英语三科 AI 伴学 App。

同学们可以先把它想象成一个“会陪你学习的 AI 精灵”。学生打开应用后，不是看到一堆表格和菜单，而是进入一个沉浸式学习空间：中间有 AI 学习伙伴，左边是学习任务和三科入口，右边是错题本、徽章、家长报告等功能。

这个精灵不是摆设。它要知道学生今天学了什么，哪里不会，下一步应该学什么，答错时应该怎么提示，过几天要不要复习。

所以我们今天讨论两个问题：

1. 外面看起来，它应该像一个有陪伴感、有科技感、适合学生使用的 App。
2. 里面跑起来，它必须有诊断、路径规划、辅导、记忆和复习这些真实能力。

## 2. 用一句大白话解释这个项目

`ai-study` 就像一个懂语数英三科的小老师，但它不是直接告诉学生答案，而是先了解学生，再带学生一步一步学。

如果学生数学应用题错了，它不是直接说答案，而是问：“你先找一找题目里有哪些已知条件？”  
如果学生古诗不会理解，它不是直接翻译，而是问：“诗里出现了哪些景物？你脑子里能想到什么画面？”  
如果学生英语单词拼错，它会把这个词放进复习计划，过几天再提醒学生复习。

这就是比赛要看的“自适应学习”。

## 3. 最终演示应该像什么

演示时，我们不随机点页面，而是讲一个完整故事。

```text
学生进入 ai-study
  -> AI 精灵问候并发起三科小诊断
  -> 学生完成数学、语文、英语题目
  -> 系统生成学生画像和薄弱点
  -> AI 推荐今日学习路径
  -> 学生进入一道数学题并答错
  -> AI 精灵分 3 步提示，不直接给答案
  -> 错题进入错题本和复习计划
  -> 家长端看到学习报告
```

这条线跑通，项目就不是空壳。

## 4. 产品体验方向：AI 精灵 + 沉浸式学习空间

前端不要做成后台管理系统。小学生不应该一打开就看到密密麻麻的表格。

我们推荐的画面结构：

| 区域 | 学生看到什么 | 背后的功能 |
| --- | --- | --- |
| 中央舞台 | AI 精灵、当前题目、对话气泡 | Agent 对话、提示、反馈 |
| 左侧边缘 | 今日任务、语文/数学/英语入口、知识地图 | 学习路径和三科切换 |
| 右侧边缘 | 错题本、徽章、家长报告、设置 | 复习、激励、报告 |
| 顶部状态 | 学生名、年级、连续学习天数 | 学生画像 |
| 底部操作 | 开始诊断、提交答案、下一步 | 学习流程控制 |

这种体验可以参考豆包一类 AI 助手的“陪伴感”，但不能照搬。我们的重点是学习，不是泛聊天。AI 精灵的表情、动作、提示，都要服务学习闭环。

## 5. 科技感不是堆颜色

科技感不等于全屏蓝紫渐变，也不等于一堆发光按钮。

适合 `ai-study` 的科技感应该是：

- 干净的深浅对比。
- 清楚的学习路径线。
- 柔和的光效和精灵动效。
- 少量高亮颜色提示重点。
- 操作按钮靠边，主舞台保持沉浸。

学生要能专注学习，老师和家长要能看懂数据。

## 6. 评委真正想看什么

| 官方评分 | 大白话解释 | 我们怎么展示 |
| --- | --- | --- |
| 智能体架构设计 | 不是聊天套壳，AI 要会规划、会记忆、会调用工具 | 展示 Agent 流程图和工具调用日志 |
| 自适应策略 | 学生答对和答错，下一步学习内容不同 | 展示路径变化和错因归类 |
| 功能完备 | 不只有一个页面，要有完整学习闭环 | 诊断 -> 路径 -> 辅导 -> 错题 -> 报告 |
| 创新体验 | 小学生愿意用，家长看得懂 | AI 精灵、沉浸式 UI、徽章、报告 |
| 商业价值 | 家庭和机构真的可能用 | 家长端、长期报告、可扩展年级 |

## 7. MVP 和最终形态怎么分

MVP 阶段，我们先做 Web 端。因为 Web 最快、最容易调试、最容易投屏展示。

但技术选择不能只看今天。我们要让它以后可以封装成 App。

| 阶段 | 目标 | 不急着做 |
| --- | --- | --- |
| MVP | Web 跑通三科完整闭环 | 不做上架 App，不做复杂账号系统 |
| 初赛增强 | 优化 UI、模型可切换、报告更专业 | 不追求教材全量覆盖 |
| 决赛增强 | 封装桌面/移动 App，加入语音和更强知识图谱 | 不做无关社交功能 |

## 8. 我们为什么这样选技术栈

先给结论：

| 模块 | 我们选什么 | 为什么适合学生团队 |
| --- | --- | --- |
| 前端 | React + Vite + TypeScript | 上手资料多，组件生态强，适合做沉浸式界面 |
| UI | Tailwind CSS + shadcn/ui + 自定义 AI 精灵 | 快速做出统一高级感，又能自己改样式 |
| AI 对话 | assistant-ui 思路或轻量自研 Chat Panel | 适合展示对话、流式输出、工具调用 |
| 后端 | FastAPI | Python 写 AI 最方便，接口文档自动生成 |
| Agent | LangGraph | 能把“诊断、规划、辅导、反思”画成流程 |
| 数据库 MVP | SQLite + SQLModel | 简单稳定，适合本地演示 |
| 数据库升级 | PostgreSQL / Supabase | 后面做多人和云端更合适 |
| 知识图谱 MVP | JSON 文件 | 学生能写，Git 能看，老师能检查 |
| 知识图谱升级 | Neo4j | 决赛阶段更专业 |
| 向量库 MVP | Chroma | 本地轻量，适合 RAG |
| App 封装 | PWA -> Tauri -> Capacitor | 先 Web，再桌面，再移动 |

这里最重要的不是背名字，而是理解选择原因：我们选的是“学生能做出来、比赛能讲清楚、后续能升级”的组合。

## 9. 数据库为什么先简单

数据库可以想象成“项目的记忆本”。

有些记忆很适合放表格里，比如学生姓名、年级、错题记录。  
有些记忆很适合放文件里，比如知识点 JSON、题库 JSON。  
有些记忆适合放向量库里，比如一段教材内容要被 AI 检索。  
有些关系适合放图数据库里，比如“分数加法”的前置知识是“通分”和“分数概念”。

MVP 阶段不需要一上来全用复杂数据库。先这样分：

| 数据 | MVP 放哪里 | 以后升级到哪里 |
| --- | --- | --- |
| 学生画像 | SQLite | PostgreSQL / Supabase |
| 错题本 | SQLite | PostgreSQL |
| 三科知识点 | JSON | Neo4j |
| 题库 | JSON | PostgreSQL |
| RAG 文档 | Chroma | Qdrant / Milvus |
| 图片/音频素材 | 本地文件 | Supabase Storage / S3 |

这样学生能理解，项目也容易跑起来。

## 10. 模型不是唯一答案

比赛公开文本没有要求必须用星火。我们做成模型可切换：

```text
LLM_PROVIDER=spark | deepseek | qwen | minimax | mock
```

星火或讯飞语音适合作为赛事契合亮点。DeepSeek、Qwen、MiniMax 都可以作为主力或备用模型。关键是代码里不要把某一家模型写死。

## 11. A-E 分工怎么理解

角色暂时用 A-E，具体姓名由老师课上确认。

| 角色 | 负责什么 | 交付什么 |
| --- | --- | --- |
| A | 后端、Agent、接口、数据库模型 | FastAPI、LangGraph、OpenAPI、学生画像 |
| B | 数学内容 | 数学知识图谱、题库、错因、Prompt |
| C | 语文内容 | 古诗/阅读/表达题库、语文 Prompt |
| D | 英语内容 | 词库、句型、复习规则、英语 Prompt |
| E | 前端和演示 | React 页面、AI 精灵、演示控制台、视频素材 |

五个人不是各做一个孤立作品。A 是中台，B/C/D 是三科能力，E 是产品体验。

## 12. 每个人到底领取哪些文档

这里要特别说清楚：每位同学不是只领取自己的角色文档。

如果只看自己的文档，就像只拿到一块拼图，不知道整张图长什么样。最后每个人都写了东西，但接口对不上、页面接不上、演示串不起来。

所以每位同学的阅读顺序是：

| 顺序 | 要看的文档 | 为什么要看 |
| --- | --- | --- |
| 1 | README | 知道仓库入口和所有文档在哪里 |
| 2 | 总 PRD、架构与协作规则 | 知道整个项目要做成什么 |
| 3 | 课堂展示讲义 | 和老师课堂讲解保持同一个理解 |
| 4 | 技术栈与架构学习指南 | 知道为什么选 React、FastAPI、SQLite、LangGraph |
| 5 | 文档领取、版本升级流程 | 知道怎么领任务、怎么提交方案、课后怎么改版 |
| 6 | Git 协作规范 | 知道怎么拉分支、提交、合并 |
| 7 | OpenAPI 接口契约 | 知道前后端怎么对接 |
| 8 | 自己的角色文档 | 知道自己第一周具体交什么 |

角色文档是“你的施工图”，总文档和规则是“全组的地图”。两类都要看。

## 13. 第一周先做什么

第一周目标不是做完，而是让五个模块第一次连起来。

| 角色 | 第一周最小成果 |
| --- | --- |
| A | `/api/v1/health` 和 3 个 mock 接口 |
| B | 5 个数学知识点、5 道题、1 个 Prompt |
| C | 5 个语文知识点、5 道题、1 个 Prompt |
| D | 5 个英语词汇节点、5 道题、1 个 Prompt |
| E | React 首页、诊断页、AI 对话页 mock |

第一周只要能连起来，就是成功。

## 14. 今天每位同学的创意怎么讲

每个创意只讲 1 分钟：

| 要素 | 说明 |
| --- | --- |
| 创意名称 | 一句话说清楚 |
| 解决什么问题 | 学生学习中真实痛点 |
| 接入哪个闭环 | 诊断、路径、辅导、错题、报告中的哪一环 |
| 需要谁配合 | A/B/C/D/E 哪些角色 |
| 最小版本 | 两周内能演示的版本 |

如果一个创意不能接入主闭环，就先放到后续版本。

## 16. 课后会怎么升级版本

现在这套文档是课前讨论版。等我看完大家的创意方案后，会把方案统一整理成最终版本。

升级时不是随便改几句话，而是按顺序改：

1. 先记录哪些创意采纳、延期、暂不做。
2. 再更新总 PRD。
3. 再更新 A-E 每个人的执行文档。
4. 如果接口变化，先更新 OpenAPI。
5. 最后重新生成 Word 讲义，保证课堂展示和开发执行是同一套说法。

这样做是为了让创意有空间，也让开发不混乱。

## 17. 这节课最后记住三句话

先让 AI 有内核，再让精灵有生命感。  
先跑通学习闭环，再打磨视觉效果。  
先学会判断技术栈，再让 AI 帮我们写代码。
