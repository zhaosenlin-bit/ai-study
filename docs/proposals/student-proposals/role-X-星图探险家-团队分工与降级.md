# 团队分工与降级方案 · 星图探险家 v1.0

> 本文档配套《执行文档》使用，详细说明团队在不同规模（4/3/2/1 人）下的分工、降级策略、产出物调整与决策时机。

---

## 0. 核心设计原则

### 0.1 不变量（任何模式都必须保留）

无论团队几个人，有 4 件事不能合并、不能砍：

1. 接口契约先行 —— A 角色必须在 W1 给出 OpenAPI 文档与 mock 数据
2. 知识库先行 —— 知识建模（B 角色的产出）必须先于前端开发
3. 演示脚本独立 —— 演示/路演准备必须有专人负责，绝不能"等做完再说"
4. 小星 Prompt 基线 —— 人设锚定的 Prompt 模板必须由懂大模型的人主笔，不能由前端/产品同学代写

### 0.2 角色间的"硬依赖"

D 数据 schema  ->  A 接口契约  ->  B 知识库  ->  C 前端 UI
       ↑                                              ↓
       └──────────  演示脚本 + 商业计划书  ←───────────┘

D 的 schema 不依赖任何人，所以 D 是 W1 第一周可以最快出活的角色。

### 0.3 并行 vs 串行的边界

| 任务 | 并行度 | 备注 |
| --- | --- | --- |
| 数据 schema 设计 | 完全并行 | D 一人独享 W1 |
| UI 设计稿 | 完全并行 | C 一人独享 W1 |
| 知识建模清单 | 完全并行 | B 一人独享 W1 |
| API 契约定义 | 阻塞 B/C/D | A 必须在 W1 周三前出 v0.1 |
| Agent Service 实现 | 依赖 B 的 Prompt | A 必须等 B 出 Prompt v1 才能联调 |
| 前端对接 | 依赖 A 的 API + B 的 Prompt 样例 | C 在 W1 用 mock，W2 末切真接口 |
| 演示视频 | 依赖所有功能 | D 在 W3 末才动 |

## 1. 4 人标准模式（推荐）

### 1.1 角色清单

| 角色 | 名字 | 核心职责 | 不可替代的关键产出 |
| --- | --- | --- | --- |
| A | Agent 架构 | 工作流 + Service + API | LangGraph 状态机图、OpenAPI 文档 |
| B | 大模型 + 知识库 | Prompt + RAG + 知识图谱 | 小星 Prompt v1、50+ 样例题、Chroma+Neo4j |
| C | 前端 + 体验 | UI + 小星形象 + 星图 | Vue3 项目骨架、星图组件、小星组件 |
| D | 产品 + 数据 + 演示 | Schema + 种子数据 + 视频 + PPT | SQLite schema、5 虚拟学生、演示脚本、20 页 PPT |

### 1.2 4 人模式的核心优势
- 每个角色都聚焦自己最擅长的领域
- 4 人可以同时推进 4 条独立分支
- W1 结束后所有分支都能 ready，并行开发效率最高
- 演示准备由专人负责，不会在最后一周崩溃

### 1.3 4 人模式的产出物清单（完整版）

#### A 同学
- LangGraph 工作流图（PNG + JSON）
- FastAPI 项目骨架
- 4 个 Service：诊断 / 推荐 / 辅导 / 反思
- OpenAPI 文档（自动生成 + 注释）
- 单元测试（覆盖率 >= 70%）
- Docker Compose 配置

#### B 同学
- 知识点清单（数学 240 + 语文 60 + 英语 60）
- 小星 Prompt 模板（对话 / 项目 / 反思）
- 50+ 道样例题（含答案 + 解析 + 知识点标注）
- Chroma 向量库
- Neo4j 知识图谱
- RAG 检索 Service
- LLM 封装层（含备用模型切换）

#### C 同学
- Figma 设计稿（3 屏 + 小星形象）
- Vue3 + Vite 项目
- 6 个核心组件：星图 / 对话 / 日记 / 项目卡 / 错题本 / 家长驾驶舱
- 小星 4 种情绪状态组件
- 动效（打字机 / 星座缩放 / 星球点亮）
- 移动端响应式适配

#### D 同学
- SQLite schema（students / errors / projects / diary）
- 5 个虚拟学生种子数据
- 10 个测试场景脚本
- 错题本 CRUD
- 5 分钟演示视频
- 20 页商业计划书 PPT
- Q&A 预案 20 题
- README + 一键部署文档

### 1.4 4 人模式的并行时序

W1 周一   ---------- Kickoff ----------
W1 周二   A 出 API v0.1 (mock)     B 列知识点   C 出设计稿   D 出 schema
W1 周三   A 评审 API               B 入库首批   C 搭骨架     D 造种子数据
W1 周四   A 实现 Service v0.1      B 写 Prompt   C 写组件     D 写测试场景
W1 周五   ---- 全员 Demo: Hello World 跑通 ----

W2        A 实现核心 Service       B Prompt 调优   C 完善组件   D 数据完整化
W2 末     ---- 4 个 feature 分支各自完成 ----

W3 周一   ---- 合并到 dev，启动联调 ----
W3        A 联调 + 优化            B RAG 优化      C 动效       D 粗剪视频

W4        A 收尾                  B 兜底话术      C 体验打磨    D 精剪 + PPT
W4 周四   ---- 全员预演 ----

## 2. 3 人降级模式

### 2.1 三种合并方案对比

| 方案 | 合并方式 | 优点 | 风险 | 推荐度 |
| --- | --- | --- | --- | --- |
| 方案 X | B + C 合并（全栈 AI + 前端） | B 写的 Prompt 可以立刻被 C 调通，迭代最快 | A 单独扛架构压力大；D 单独扛演示压力大 | 五星 强烈推荐 |
| 方案 Y | A + D 合并（架构 + 演示） | 后端与产品决策一致 | 无人专注前端，UI 容易粗糙 | 二星 可用 |
| 方案 Z | C + D 合并（产品 + 前端） | 体验设计一气呵成 | 后端无人专注，联调期极易延期 | 一星 不推荐 |

强烈推荐 方案 X（B + C 合并）。理由：
1. B 和 C 的协作最频繁（Prompt 写完就要 UI 验证）
2. 合并后节省"跨人沟通"成本，Prompt 调整 -> UI 调整可在 1 小时内闭环
3. A 单独做架构反而更专注（不需要一边写 Service 一边切去管 Prompt）
4. D 单独做演示与产品，反而更聚焦（演示材料本来就要专人打磨）

### 2.2 方案 X · B + C 合并后的产出物调整

新角色命名：B+C = E 同学（全栈 AI 与体验）

E 同学的产出清单：
- 全部 B 的产出（知识点 / Prompt / Chroma / Neo4j / RAG）
- 全部 C 的产出（设计稿 / Vue3 / 组件 / 动效）
- 新增：负责 E 同学侧的 mock 数据先行（弥补 A 的接口 mock 不足）
- 风险点：动效质量可能下降 -> 必须 W4 末留出 2 天专门打磨

### 2.3 3 人模式下的关键调整

1. W1 周三必须完成的事：
   - A 出 OpenAPI v0.1（不变）
   - E 同时启动 B 与 C 两部分工作
   - D 启动数据 schema 与演示大纲

2. W1 末的 Demo 标准降低：
   - 4 人模式：前后端联调跑通
   - 3 人模式：E 用 mock 数据跑通前端 + A 跑通最小后端（不必联调）

3. W3 联调延期 1 天：
   - 4 人模式：W3 周一开始联调
   - 3 人模式：W3 周二开始联调（E 多 1 天写前端）

4. 演示视频长度压缩：
   - 4 人模式：5 分钟
   - 3 人模式：4 分钟（D 单独负责，可压缩）

### 2.4 3 人模式并行时序（方案 X）

W1 周一   ---------- Kickoff ----------
W1 周二   A 出 API v0.1     E: B 知识点 + C 设计稿     D: schema
W1 周三   A 实现 Service    E: B Prompt + C 骨架        D: 种子数据
W1 周四   A 继续 Service    E: B RAG + C 组件           D: 测试场景
W1 周五   -- Demo: A 最小后端 + E mock 前端 --

W2        A 核心 Service    E: B Prompt 调优 + C 组件    D: 数据完整化
W2 末     -- A 完成 + E 完成 --  D 完成 --

W3 周二   ---- 合并到 dev，启动联调 ----  (比4人模式晚1 天)
W3        A 联调            E: 联调 + 动效               D 粗剪视频
W3 周五   -- 完整闭环演示通过 --

W4        A 收尾            E: 兜底 + 体验打磨           D 精剪 + PPT
W4 周四   -- 全员预演 --
W4 周五   -- 提交 --

### 2.5 3 人模式的风险

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| E 同学过载 | 高 | W1 周三站会必须评估；过载则把 C 的非核心组件（家长驾驶舱动效）砍掉 |
| 动效质量下降 | 中 | W4 单独留 2 天专门打磨动效 |
| D 单独扛演示压力大 | 中 | W2 周五 D 必须出"演示脚本草稿"让全员评审 |
| 缺少"小星形象"专业设计 | 中 | E 用 imagegen 或 AI 生成小星形象；不必追求手绘 |

## 3. 2 人降级模式

### 3.1 两种合并方案对比

| 方案 | 合并方式 | 优点 | 风险 | 推荐度 |
| --- | --- | --- | --- | --- |
| 方案 P | P1 = A + B（架构 + AI）<br>P2 = C + D（前端 + 演示） | 两端各有一位"全能 owner"，边界清晰 | 演示视频与商业计划书可能草率 | 四星 推荐 |
| 方案 Q | P1 = A + B + D（后端 + AI + 演示）<br>P2 = C（前端单兵） | 前端专注 | P1 过载；演示素材可能粗糙 | 二星 不推荐 |
| 方案 R | P1 = A + D（架构 + 演示）<br>P2 = B + C（AI + 前端） | 后端与演示协同好 | P2 工作量极大 | 二星 可用 |

推荐 方案 P：两位"准全栈 owner"对接，沟通成本最低。

### 3.2 方案 P · 工作分配

#### P1 同学（A + B 合并）
核心定位：让 Agent 跑起来 + 让 AI 答得对

- LangGraph 工作流 + Service + API（核心）
- OpenAPI 文档
- 小星 Prompt + 知识图谱
- RAG 检索
- D 角色职责：P1 还要负责"演示的工程支撑"（数据 mock + 演示脚本的技术可行性），但不负责视频拍摄与 PPT 设计

#### P2 同学（C + D 合并）
核心定位：让产品看起来很美 + 让演示讲得动人

- Vue3 全栈开发（前端主导）
- 全部 UI / 组件 / 动效
- 演示视频拍摄与剪辑
- 商业计划书 PPT
- 种子数据准备（不依赖 P1）

### 3.3 2 人模式下的关键调整

1. MVP 范围必须砍：
   - 砍掉：家长驾驶舱（v1.0 不做家长端）
   - 砍掉：小星 4 种情绪（只做 1~2 种）
   - 砍掉：移动端响应式（只做桌面端）
   - 砍掉：错题本 CRUD（v1.0 只展示，不让用户编辑）
   - 保留：5 题诊断 + 星图 + 小星对话 + 火星基地 1 节完整 + 小星日记（基础版）

2. 演示视频简化：
   - 4 人模式：5 分钟
   - 3 人模式：4 分钟
   - 2 人模式：3 分钟（只演示 1 节项目，不演示全部 6 节）

3. 周节奏更紧：
   - 每日站会延至 30 分钟（需要更细的同步）
   - 每周末必须有一次"代码 review + 互相 demo"

### 3.4 2 人模式并行时序

W1 周一   ---------- Kickoff ----------
W1 周二   P1: API + 知识点         P2: 设计稿 + schema
W1 周三   P1: Service + Prompt    P2: 骨架 + 种子数据
W1 周四   P1: 知识库 + RAG        P2: 核心组件
W1 周五   -- Demo: 最小闭环跑通 --

W2        P1: 核心能力            P2: UI + 组件
W2 末     -- MVP 砍版功能完成 --

W3        P1: 联调                P2: 动效 + 视频拍摄
W3 周五   -- 完整闭环 + 视频粗剪 --

W4        P1: 收尾                P2: PPT + 视频精剪
W4 周四   -- 全员预演 --
W4 周五   -- 提交 --

### 3.5 2 人模式的风险

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 任一人缺席 = 项目停摆 | 极高 | 每日强制 commit；关键决策必须落 PR description |
| 工作量严重过载 | 高 | W1 周三必须砍 MVP 范围（见 3.3） |
| 演示视频粗糙 | 中 | P2 在 W2 周五必须锁定脚本，否则视频来不及 |
| 一方进度拖延拖累另一方 | 高 | W2 周五必须有一次"feature freeze"，之后只修 bug 不加新功能 |

## 4. 1 人极限模式（不推荐，仅供参考）

### 4.1 适用场景
- 个人参赛、练手作品、不指望获奖
- 或者团队只有 1 个能投入时间的人，其他人只是挂名

### 4.2 1 人模式的 MVP 砍版（必须再砍）

- 只做：星图可视化（静态）+ 小星对话（人格化）+ 火星基地 1 节任务
- 不做：日记（改为日志打印）/ 不做：家长端 / 不做：错题本 / 不做：动效

### 4.3 1 人模式的时序
- W1：API + Schema + 知识点 + 最小前端
- W2：核心对话 + 1 节项目
- W3：联调 + 视频
- W4：PPT + 提交

### 4.4 1 人模式几乎不可能拿奖
除非参赛者本人就是评委 / 自家比赛 / 提交作品门槛只要求 Demo 而不要求完整度。

## 5. 模式选择决策树

你有几位靠谱的、能在 4 周内每周投入 15+ 小时的队友？

├── 4 位（或更多）   ──>  【4 人标准模式】

├── 3 位
│   │
│   ├── 其中至少 1 位全栈能力强 ──>  【3 人模式·方案 X：B+C 合并】(推荐)
│   │
│   └── 没有全栈，全是专才 ──>  【3 人模式·方案 Y：A+D 合并】

├── 2 位
│   │
│   ├── 2 位都是全栈 ──>  【2 人模式·方案 P】
│   │
│   └── 1 位偏后端 1 位偏前端 ──>  【2 人模式·方案 P】
│   │     (正好对应，一人 A+B 一人 C+D)
│   │
│   └── 2 位都偏产品/演示，无技术主力 ──>  招人，否则不要参赛

└── 1 位
    │
    ├── 个人练手 / 提交门槛低 ──>  【1 人极限模式】
    │
    └── 正式参赛 ──>  强烈建议拉到至少 2 人再参赛

## 6. 决策时机与锁定规则

### 6.1 何时锁定模式？
- W1 周一 Kickoff 前：必须确认模式
- W1 周三站会：必须根据前 2 天进度决定是否调整

### 6.2 调整模式的代价
- 一旦进入 W2，调整模式的代价 = 砍 MVP + 重排时间
- 一旦进入 W3，不再调整模式（只能砍功能）

### 6.3 降级的硬性触发条件
下列任一条件满足，必须降级：

1. W1 周五全员 Demo 有超过 1 人无 PR
2. 任何角色在 W1 累计投入 < 10 小时
3. 团队成员预计 W2 后退出
