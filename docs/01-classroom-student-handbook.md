# ai-study 课堂展示与学生执行手册

版本：v0.2  
日期：2026-08-18  
用途：给老师课堂讲解、给学生理解项目、给 A-E 五个角色开发时照着执行。  
项目名：`ai-study`  
仓库：https://github.com/zhaosenlin-bit/ai-study.git

## 0. 老师先讲给学生听的 3 句话

第一，这个项目不是做一个“会聊天的网页”。比赛真正想看的是一个 AI 伴学 Agent：它要先了解学生，再规划学习路径，再用引导式问题帮助学生，最后记住学生的问题并调整下一次学习。

第二，五个人不是各做各的页面。我们每个人只负责一块，但所有代码必须按统一目录、统一接口、统一数据格式汇到一起，最后才会变成一个完整作品。

第三，今晚每个人的创意都可以提，但最终只保留能服务“诊断 -> 路径 -> 辅导 -> 复盘”闭环的创意。漂亮但不影响闭环的东西排后面。

## 1. 项目到底要做什么

`ai-study` 是一个小学 3-6 年级语文、数学、英语三科 AI 学习伙伴。

学生进入系统后，AI 不是直接问“你想学什么”，而是先做诊断。诊断可能包含一道数学应用题、一段语文阅读、一组英语单词或对话。学生作答后，系统会更新学生画像，例如“数学分数理解薄弱”“语文阅读主旨概括较弱”“英语食物类单词容易拼错”。

接着，Agent 会根据学生画像和三科知识图谱生成今日学习路径。学生如果卡住，AI 不直接告诉答案，而是像老师一样给台阶：先问思路，再给提示，再给关键步骤，最后让学生自己补出答案。

学习结束后，错题会进入错题本，系统安排复习时间，家长端能看到一份简单报告：孩子今天学了什么、哪里薄弱、明天建议练什么。

## 2. 比赛评分翻译成学生能懂的话

| 官方评分 | 学生要理解成什么 | 我们怎么证明 |
| --- | --- | --- |
| 智能体架构设计 30 分 | 评委不想看普通聊天框，想看 AI 会规划、会记忆、会调用工具 | 展示 Agent 流程图、接口日志、工具调用记录 |
| 自适应策略 25 分 | 每个学生薄弱点不同，下一步学习内容也要不同 | 展示同一题答对/答错后路径变化 |
| 功能完备程度 20 分 | 不能只有一个功能，必须是一条完整学习闭环 | 演示诊断、推荐、辅导、错题本、家长报告 |
| 创新性与体验 15 分 | 小学生愿意用，家长看得懂 | AI 伙伴、徽章、路径地图、清晰报告 |
| 商业价值 10 分 | 这个东西以后能给家庭、机构或学校用 | PPT 讲清楚家庭伴学场景和推广方式 |

## 3. 最终演示要长什么样

演示不是随机点页面，而是一条固定故事线。

1. 老师或学生打开 `ai-study`。
2. 选择一个四年级 demo 学生。
3. AI 伙伴说：“我们先做一个 5 分钟小诊断。”
4. 学生完成三科诊断题。
5. 系统显示三科掌握度和薄弱点。
6. AI 推荐今日学习路径。
7. 学生进入数学辅导，故意答错一道题。
8. AI 分三步提示，不直接给答案。
9. 错题进入错题本，并安排复习。
10. 家长端显示报告：薄弱点、错因、建议任务。

如果这 10 步跑通，项目就有了比赛最核心的骨架。

## 4. 五个人的角色边界

角色暂时用 A-E，课上由老师确认具体姓名。

课堂确认时可以使用 [A-E 角色分工确认看板](roles/00-role-assignment-board.md)。

| 角色 | 分支 | 一句话职责 | 最关键产出 |
| --- | --- | --- | --- |
| A | `feature/agent-core` | 让 AI 真正像 Agent 一样工作 | FastAPI、LangGraph、接口、学生画像、路径规划 |
| B | `feature/subject-math` | 把数学知识点、题目、错因做好 | 数学知识图谱、题库、错因标签、数学 Prompt |
| C | `feature/subject-chinese` | 把语文阅读、古诗、表达引导做好 | 语文知识图谱、题库、语文 Prompt |
| D | `feature/subject-english` | 把英语单词、句型、复习做好 | 英语词库、题库、复习调度、英语 Prompt |
| E | `feature/web-integration-demo` | 把所有能力变成能看的网页和演示 | React 前端、家长端、演示控制台、录屏脚本 |

## 5. 每个人今晚需要交什么创意方案

每位同学的创意方案不要写成大作文，按这个模板写：

| 项目 | 要写什么 |
| --- | --- |
| 创意名称 | 例如“错题复习小地图”“AI 古诗画面引导” |
| 对应评分 | 架构、自适应、完整度、体验、商业价值中的哪一个 |
| 学生收益 | 小学生用它能解决什么学习问题 |
| 需要模块 | 前端、后端、数学、语文、英语、数据中的哪些 |
| 两周可做版本 | 最小能演示的版本是什么 |
| 风险 | 会不会太难、太耗时、依赖 Key 或素材 |

筛选原则：

- P0：能让主闭环更完整，必须优先做。
- P1：能让演示更好懂，可以做。
- P2：只是好看但不影响闭环，最后有时间再做。

## 6. 不会开发时先看这里

### 6.1 你不是一个人从零开始

每个角色都有自己的目录和验收标准。你只要先把自己目录里的最小版本做出来，不需要一开始就理解全项目。

### 6.2 每个人第一天只做 3 件事

1. 把仓库拉下来。
2. 切到自己的分支。
3. 在自己的目录放一个最小可用样例。

例如数学负责人第一天不需要做完全部题库，只需要提交 5 个数学知识点、5 道题、1 个 Prompt 样例，让 A 和 E 能先联调。

### 6.3 不允许“等别人做完我再做”

如果后端没好，前端用 mock 数据。  
如果三科题库没全，后端用样例数据。  
如果语音 Key 没好，前端先用文本按钮和 mock 音频。  
如果模型不稳定，先用 `LLM_PROVIDER=mock` 跑完整流程。

## 7. Git 操作说明

第一次拉仓库：

```bash
git clone https://github.com/zhaosenlin-bit/ai-study.git
cd ai-study
```

老师创建好 `develop` 后，每个同学从 `develop` 拉自己的分支：

```bash
git checkout develop
git pull origin develop
git checkout -b feature/subject-math
```

每天提交：

```bash
git status
git add .
git commit -m "feat(math): add first diagnosis questions"
git push -u origin feature/subject-math
```

不要直接改 `main`。  
不要提交 `.env`。  
不要私下改接口。  
不要把大视频、压缩包、临时文件提交进仓库。

## 8. 模型选择规则

比赛公开文本没有要求必须用星火。我们可以用 DeepSeek、Qwen、MiniMax，也可以接星火。正确做法是把模型做成可切换：

```text
LLM_PROVIDER=spark | deepseek | qwen | minimax | mock
```

建议策略：

- 主流程先用最稳定、最容易接通的模型跑起来。
- 讯飞星火或讯飞语音作为赛事契合亮点保留。
- PPT 中说明每个模型承担什么任务。
- 代码里不要把某一家模型写死。

## 10. 接口契约为什么重要

接口契约就是五个人之间的“共同语言”。

前端不能猜后端字段，后端不能猜题库格式，三科模块不能每个人写一种数据结构。所有人都按 `docs/api/openapi-contract-v0.yaml` 来。

如果要改接口：

1. 先在群里说清楚为什么要改。
2. 先改 OpenAPI 文档。
3. A 和 E 确认。
4. 再改代码。

## 11. A 角色：Agent 后端负责人详细说明

A 的任务最像“总控台”。你不需要写所有题目，也不需要做漂亮页面，但你要让所有模块能连起来。

第一阶段先做：

1. FastAPI 启动成功。
2. `/api/v1/health` 返回 OK。
3. `/api/v1/diagnosis/start` 能返回 mock 诊断题。
4. `/api/v1/diagnosis/submit` 能根据答案生成薄弱点。
5. `/api/v1/agent/chat` 能返回一条引导式回答。

第二阶段再做：

1. 接入三科题库。
2. 接入模型网关。
3. 接入学生画像和错题本。
4. 输出 Agent 工具调用日志。
5. 让路径规划根据掌握度变化。

A 的验收：

- Swagger 能打开。
- 前端能调通核心接口。
- 同一个学生答错和答对后，推荐路径不同。
- 日志能看到 Agent 的诊断、规划、辅导、反思节点。

## 12. B 角色：数学负责人详细说明

数学是最适合展示自适应的模块，因为错因很清楚。

B 第一阶段先做：

1. 30 个 3-4 年级数学知识点。
2. 30 道诊断题。
3. 10 道错题复习题。
4. 3 个 Prompt：诊断、分步提示、错因分析。
5. 1 条完整数学演示脚本。

数学题不要只写答案，要写错因。比如：

```json
{
  "error_type": "concept_missing",
  "reason": "学生把分母相加，说明没有理解通分"
}
```

B 的验收：

- A 能读取数学 JSON。
- E 能在前端展示数学题。
- 演示中 AI 能分步提示，而不是直接给答案。

## 13. C 角色：语文负责人详细说明

语文模块不要做成“背答案”。重点是引导学生理解文本、想象画面、表达观点。

C 第一阶段先做：

1. 10 个古诗知识点。
2. 10 个阅读理解知识点。
3. 10 个词语/表达知识点。
4. 60 道题或材料条目。
5. 3 个 Prompt：古诗引导、阅读证据定位、表达支架。

语文引导例子：

学生问：“这首诗是什么意思？”  
AI 不要直接整首翻译，而是问：“你先找一找，诗里出现了哪些景物？这些景物让你想到什么画面？”

C 的验收：

- 古诗或阅读至少能完整演示一轮。
- 每道题有知识点和错因标签。
- AI 回答适合小学生，不要太成人化。

## 14. D 角色：英语负责人详细说明

英语模块重点展示单词记忆、句型使用和复习调度。

D 第一阶段先做：

1. 40 个核心词汇节点。
2. 20 道单词题。
3. 10 组情景对话。
4. 10 道句型补全题。
5. 复习调度规则。

复习规则先用简单版本：

| 结果 | 下次复习 |
| --- | --- |
| 答错 | 1 天后 |
| 答对 1 次 | 3 天后 |
| 答对 2 次 | 7 天后 |
| 答对 3 次 | 15 天后 |

D 的验收：

- 能展示一个错词进入复习计划。
- 能展示一段简单情景对话。
- 如果语音没接通，也要有文本版演示。

## 15. E 角色：前端与演示负责人详细说明

E 的任务是把大家的成果变成“评委能看懂”的作品。

统一技术栈：

```text
React + Vite + TypeScript
```

第一阶段先做页面空架子：

1. 学生首页。
2. 诊断页。
3. AI 对话页。
4. 学习路径页。
5. 错题本页。
6. 家长报告页。
7. 演示控制台。

前端可以先用 mock 数据，不要等后端。

E 的验收：

- 能一键切换 demo 学生。
- 能按演示脚本走完整流程。
- 页面没有明显空按钮。
- API 失败时有提示。
- 能录制 3-5 分钟演示视频。

## 17. 每日站会怎么说

每个人只说 3 件事：

1. 我昨天完成了什么。
2. 我今天要完成什么。
3. 我卡在哪里，需要谁帮忙。

不要说“我研究了一下”。要说具体产出，例如“我提交了 10 道数学题”“我把诊断接口 mock 跑通了”。

## 18. PR 描述怎么写

每次提 PR 写清楚：

```text
做了什么：
- 新增 10 道四年级数学诊断题
- 增加 concept_missing 和 calculation_error 两类错因

怎么验收：
- 打开 data/question_bank/math/grade4.json 能看到题目
- question_id 为 math_q_0001 到 math_q_0010

还缺什么：
- 还缺 20 道复习题
```

## 19. 最容易出问题的地方

| 问题 | 后果 | 预防 |
| --- | --- | --- |
| 每个人自己定义字段 | 最后合不起来 | 统一看 OpenAPI 和数据样例 |
| 前端等后端 | 页面做不完 | 先用 mock |
| 题库没有错因 | 自适应讲不出来 | 每题必须有知识点和错因 |
| AI 直接给答案 | 不符合赛题 | Prompt 必须要求分步引导 |
| 只做单科 | 三科方案不明显 | 每科至少一条演示流程 |
| 不提交 Git | 看不出分工 | 每天至少一次小提交 |

## 22. 学生拿到任务后的第一条消息模板

每位同学确认角色后，在群里发：

```text

今晚我先完成 ______。
明天我会提交到分支 ______。

需要谁配合我 ______。
```

这样老师能马上知道谁清楚、谁还需要帮忙。
